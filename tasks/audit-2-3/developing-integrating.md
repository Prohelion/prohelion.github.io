# Structure audit: Developing_with_Profinity and Integrating_to_Profinity (Profinity 2.3)

Read-only audit. No docs were edited. Scope is the 24 pages below, read in full (headings, procedures, examples, tables), with duplicates confirmed by grep across the docs root `Profinity_Software/Profinity_Version_2.3/` and the wider `docs/` tree.

## Method and rules applied

- Rules: STYLE_GUIDE.md sections 1 (front matter, page types, heading hierarchy), 5 (lists and procedures) and the page-types table. Reviewer notes in "Camerons Document Review notes.md" applied to the Custom Components index (DBC and Dashboard sections). Other reviewer notes concern pages outside these sections and were not applied.
- Word counts from `wc -w` (includes front matter and code).
- Declared type: no page in either section has a `type:` field. Front matter is `title` and `description` only (no `owner` or `last_reviewed`). Every row shows `none`.
- Heading case: scripted scan plus manual check against sentence-case rules. "Related Documentation" counts as one Title Case heading. Product and feature names (Custom Components, Tag Relay, MCP Server) are treated as keeping their form.
- Links: scripted check that every relative `.md` link resolves on disk. Anchors not checked.
- Duplicates: distinctive phrases grepped across `docs/`.
- Helper scripts are in `scratchpad/audit/checks.py` (not a report).

## Section-level observations

- Front matter: none of the 24 pages declares `type:`, and none has `owner` or `last_reviewed`. Style section 1 requires all three on new and refactored pages. Add `type` as each page is rewritten. `docs/internal/` in the docs root also holds working files (engineering open questions, documentation TODO, writer brief, a licence test checklist); confirm they are excluded from the published site.
- Script pages: the five script-type pages (Run, Receive, Service, Tag Change, Rule) do not match any single page type. They share one shape that fits `component` (purpose, trigger diagram, quick start, settings table, example, troubleshooting). Move their settings out of prose and into tables.
- Duplication is the largest problem. Trigger Overlap is explained in four pages; the minimum receive example and CAN text appear in both CANBus and ReceiveScripts; the computed-tag example appears in TagChangeScripts and Tags/Script_Driven_Derived_Tags; the Custom Component DBC and Dashboard text duplicates Components/Custom_Components/index.md; the token and 401/403 text appears in APIs, MCP and Connect_Profinity_to_AI; "enable scripting" appears in four places. Give each fact one home and link to it.
- Reviewer notes: the Custom Components index DBC File and Dashboard sections should be removed and linked, because their content already lives at Components/Custom_Components/index.md. The Script-Driven Derived Tags note matches the existing Tags/Script_Driven_Derived_Tags.md page, so the computed-tag example in TagChangeScripts should move there.
- Length: MCP_Server (2,863 words), Custom_Components index (1,850), Tags (1,157), CANBus (1,062) and APIs index (1,027) each mix two to four types. Split them before tagging. The MCP tool reference alone is about 1,500 words and is the clearest reference candidate.
- Diagrams: almost every figure in these sections is a UI screenshot. Concept pages that need a diagram: Service lifecycle; trigger flow for Tag Change, Receive and Rule; Custom Component files to run, pack and install; plugin anatomy; token and historical-query flow; MCP client to tools to permission scope. Component_Types places a plugin-packaging figure on a comparison page, and the Scripting index caption does not describe its image.
- Examples: about 70 code blocks, counting each language tab, and none has evidence it was run. Script samples can be checked with `profinity-script sim`, YAML samples with `profinity-component-pack validate`, and REST and MCP samples against a running instance. Add this as a docs build check rather than a manual review.
- First-success paths: Integrator: there is none in Integrating_to_Profinity. The closest is How_To_Guides/Connect_Profinity_to_AI.md (1,119 words, MCP-only, how-to shape). There is no tutorial for a first authenticated REST call, and the APIs page gives only a curl line. Developer: How_To_Guides/Write_Your_First_Script.md (1,279 words, outside these sections) gives a first run with prerequisites, steps and troubleshooting, and Scripting/index links to it, but it is a how-to, not a tutorial. The zero-engine route (`profinity-script new`, then `sim`) is buried in SDK.md. Recommend one tutorial for each, each with a checkpoint after every stage.
