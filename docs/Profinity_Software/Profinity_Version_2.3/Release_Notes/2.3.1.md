# Profinity 2.3.1

Profinity 2.3 introduces commercial editions with offline licensing, Profinity AI, derived tags, publishers and subscribers, role-based security with single sign-on and two-factor authentication, a visual dashboard editor, and the Profinity Mobile app. It also changes where Profinity stores data on Linux, how `/api/v2` reports errors, and which features an instance without a licence can use. Anyone upgrading from 2.2 should read [Upgrading From 2.2](#upgrading-from-22) and [Breaking Changes](#breaking-changes) before they upgrade a production system.

This release is for operators, administrators, integrators and OEMs who deploy Profinity on Windows, Linux, macOS and Docker.

## What Is New

### Editions and Licensing

Profinity 2.3 limits commercial features by edition (Desktop, Server and Enterprise) using a signed licence file that Profinity validates offline, with no activation service. An instance with no valid licence is unlicensed: it keeps the core product (the local web interface, the REST API, tags, dashboards, rules, device components, CAN utilities and file loggers) and loses the features that need an edition. A new installation that is not a Desktop host starts a one-time 14-day local trial with Server edition features (on builds that offer it), and drops to the unlicensed set when the trial ends. Remote web access, user and role administration, two-factor authentication, Profinity AI, the Email, Slack, Webhook and MQTT rule actions and the data relay components need the Server edition, and single sign-on and SCIM provisioning need Enterprise. The **ADMIN > License** page shows the state, the edition, the machine fingerprint to send to Prohelion, and what each feature is blocked by. See [Licensing](../Administration/Licensing.md) for the full feature table.

### Profinity AI

Profinity AI adds a chat assistant inside the web interface that answers questions about a running instance by reading live tags, alert rules and alert history, and answers how-to questions from the Profinity documentation. An administrator configures one provider for the whole instance under **ADMIN > System Configuration**, and users with the **Profinity AI** permission open the chat from the **Profinity AI** entry in the side menu. The built-in MCP (Model Context Protocol) server lets other AI tools read the same data, and AI Skills packs help Claude Code, Cursor, Codex and ChatGPT build dashboards, rules, collections, derived tags and scripts against your instance. Profinity AI and the MCP server need the Server edition. See [Profinity AI](../Profinity_AI/index.md), [AI Skills](../Profinity_AI/AI_Skills.md) and [MCP Server](../Integrating_to_Profinity/MCP_Server.md).

### Derived Tags

A derived tag is a tag whose value Profinity calculates from an expression over other tags. It appears in the tag tree and behaves like any other tag for dashboards, rules, history and the API. Derived tags are created in the Derived Tags editor in the tag utilities menu, and are included in every edition. See [Derived Tags](../Tags/Derived_Tags.md).

### Publishers and Subscribers

The MQTT Publisher and the new Webhook Publisher push the values of a tag collection to a broker or a URL, and the MQTT Subscriber receives Sparkplug B data into read-only tags. The MQTT Logger is now the MQTT Publisher, and the Email, Slack, Webhook and MQTT rule actions send a message when a rule fires. These components need the Server edition. See [MQTT Publisher](../Components/Publishers_and_Subscribers/MQTT_Publisher.md), [Webhook Publisher](../Components/Publishers_and_Subscribers/Webhook_Publisher.md) and [MQTT Subscriber](../Components/Publishers_and_Subscribers/MQTT_Subscriber.md).

### Security and Identity

Profinity 2.3 replaces security groups with role-based access control (RBAC): each user is assigned roles, each role holds a list of the 27 available permissions, and changing a user's roles or a role's permissions revokes that user's active sessions. A site chooses one sign-in method, Local or SSO, and a Local site can require two-factor authentication for every local user, with recovery codes and an optional remember-this-device period. Administrators can reset another user's password or two-factor enrolment, and service accounts with long-lived tokens support automation and MCP. Component and collection visibility lets an administrator hide a component or tag collection from chosen roles, and the password policy and session policy are set under **ADMIN > System Configuration**. Firmware passcodes are no longer saved in the profile, and users enter them when they unlock a component's firmware. See [Roles and Permissions](../Administration/Users_and_Access/Roles_and_Permissions.md), [SSO and Sign-In](../Administration/System_Configuration/Security/SSO_and_Sign_In.md) and [Component and Collection Security](../Administration/Users_and_Access/Component_And_Collection_Security.md).

### Tags, Rules and Alerts

The tag layer adds the Tag Explorer for browsing the tag catalogue with quality indicators, visual editors for collections and rules, and an Alerts Log with **Active** and **History** tabs, live indicators on dashboards and in the Tag Explorer, and dwell and deadband evaluation. A rule can run a script on alert (C#, Python or Lua), and the script receives the tags that triggered the rule. Rule scripts and the Email, Slack, Webhook and MQTT actions need the Server edition. Tag paths can now be absolute (starting with `/`) or relative to a component, and the **Tag tree path** setting mounts a component under a parent path. See [Tags](../Tags/index.md), [Alerts](../Tags/Alerts.md) and [Tag Tree Path](../Tags/Tag_Tree_Path.md).

### Components, Plugins and Dashboards

The Plugin Manager under **ADMIN > Components & Plugins** uploads, enables, disables and reloads external DLL plugins (`.nupkg` or zip). Custom Components support actions, firmware scripts and settings maps, and `profinity-component-pack` packs them for installation. The Dashboard component is a YAML-only profile component, and a menu layout editor places profiles and components in the side menu. The visual editor is now the main way to edit dashboards: add, arrange and bind widgets in **DESIGN** mode, with the **YAML** tab as a fallback, and existing YAML dashboards keep working and open in the visual editor. Charts accept several data sources, and map bindings take latitude and longitude. See [Visual Editor](../Customising_Profinity/Dashboards/Visual_Editor.md), [Components and Plugins](../Administration/Components_and_Plugins.md) and [Component Pack CLI](../Developing_with_Profinity/Custom_Components/Component_Pack_CLI.md).

Every component that holds a connection now starts even when the other end is down, shows **Error** with the reason in the log, and connects by itself when the broker, device, server or database appears, including after a rejected login is corrected. See [Connections and Reconnecting](../Components/Connections_and_Reconnecting.md).

### Installation and Mobile

Linux and macOS installs use a one-script installer (`install.sh`) and `update.sh`, with archives for each processor architecture, and Prohelion publishes a Docker image for `linux/amd64`, `linux/arm64` and `linux/arm/v7`. On Linux the default data directory is now `/var/lib/prohelion/profinity`, and `PROFINITY_HOME` overrides it on every platform. Profinity Mobile for iOS and Android finds servers on the local network through a UDP heartbeat (port 49025 by default) and signs in with a password or a Kiosk Mode user. See [Linux and macOS Installation](../Installation/Zip_Installation.md), [Docker Installation](../Installation/Docker_Installation.md), [Artefacts Directory](../Installation/Artifacts_Directory.md) and [Profinity Mobile](../Mobile/index.md).

## Upgrading From 2.2

Upgrade a production system in this order.

1. Back up the `config/` and `profiles/` folders of the artefacts directory, together with `license/` and `certificates/`, before you install 2.3. These folders are named `Config` and `Profiles` until 2.3 starts for the first time. On a 2.2 system the artefacts directory is `%LOCALAPPDATA%\Prohelion\Profinity` on Windows and `~/.local/share/Prohelion/Profinity` on macOS and Linux.
2. Install Profinity 2.3 and start it once. First start moves data from older locations into the 2.3 artefacts directory, renames `Config`, `Profiles` and `Logs` to lowercase, rewrites `security.yaml` and `profile.yaml` in the 2.3 camelCase format when it loads them, and rewrites `config.yaml` the next time it is saved. Profinity does not move data when `PROFINITY_HOME` is set, so copy anything you need into that location yourself.
3. Open **ADMIN > License** and confirm the state and the edition. A 2.2 installation upgraded without a licence file is unlicensed once any trial ends, and remote web access, user and role administration, two-factor authentication, Profinity AI and the Email, Slack, Webhook and MQTT rule actions stop being available until you upload a licence. See [Licensing](../Administration/Licensing.md).
4. Sign in as an administrator, open **ADMIN > Users & Groups**, and check the **Roles** tab and each user's assigned roles. Change the default `admin` password if you have not already; a default `admin` account that Profinity creates must change its password at first sign-in.
5. Open **ADMIN > System Configuration** and confirm the **Sign-in method**, the password policy and the SSO, SCIM and SIEM settings.
6. Open **ADMIN > Logs** and read the messages from first start. On Linux, the migration messages name each file that moved.
7. Open each custom dashboard in the dashboard editor and confirm it loads without schema errors.
8. Unlock the firmware of each Gen2 and Rinstrum component once and enter its passcode again, because 2.3 does not keep passcodes in the profile.
9. Run every integration that calls `/api/v2` against a test instance, because error responses changed (see [REST API Errors](#rest-api-errors)).
10. Open each BACnet component and set **Device instance** to the instance of its device, because Profinity now checks it (see [BACnet Device Instance](#bacnet-device-instance)).

To return to 2.2, reinstall 2.2 and restore the backup you took in step 1.

!!! info "Linux and Docker Data Locations"
    On Linux, 2.3 moves data from `~/.local/share/Prohelion/Profinity` (the 2.2 location) to `/var/lib/prohelion/profinity` the first time it starts. A Docker container follows the same rule unless `PROFINITY_HOME` is set, and the Docker compose file Prohelion publishes sets it to the container path that holds your mounted data. For a Docker upgrade, set `PROFINITY_HOME` to the container path of your existing mount, keep that mount, and copy any legacy `Config` and `Profiles` folders into it before you start the 2.3 image. See [Docker Installation](../Installation/Docker_Installation.md).

## Breaking Changes

### Security File Format

All installations that upgrade from 2.2 are affected. Security groups are removed: users receive assigned roles, and each role holds a list of permissions. Profinity migrates `security.yaml` automatically when it loads the file and writes `version: "2.3"` back. The default **Administrators** role holds every permission, including **MCP integration**.

Hand-edited `security.yaml` files, such as those kept in source control, need the new keys. On disk the keys are camelCase: `securityGroups` becomes `roles`, a user's `securityGroups` becomes `assignedRoles`, a group's `securityRoles` becomes the role's `permissions`, and `Version` becomes `version: "2.3"`. Check that `roles` and `assignedRoles` are present before you start Profinity, and review role assignments afterwards. See [Roles and Permissions](../Administration/Users_and_Access/Roles_and_Permissions.md).

### Settings in config.yaml

Administrators who configured OIDC single sign-on, SCIM provisioning or SIEM export in `security.yaml` now set them in `config.yaml`, under **ADMIN > System Configuration** in the **Security** section. `security.yaml` keeps users, roles, two-factor secrets and external identity links. Saving System Configuration restarts Profinity.

### Site Sign-In Method

The per-user sign-in mode and the per-role two-factor setting are replaced by one site policy: an administrator chooses Local or SSO, and on a Local site can require two-factor authentication for every local user. SSO users sign in through the identity provider and link their account under **External identity links** in user settings. A site cannot mix Local and SSO sign-in. See [SSO and Sign-In](../Administration/System_Configuration/Security/SSO_and_Sign_In.md).

### Licensing

Features that were available without limit in 2.2 now depend on the edition (see [Editions and Licensing](#editions-and-licensing)). A 2.2 installation without a licence file loses remote web access, users and roles, two-factor authentication, Profinity AI, scripting, the InfluxDB v2, InfluxDB v3 and TAG SQL historians, themes, and the Email, Slack, Webhook and MQTT rule actions and rule scripts that run on alert. Upload a licence before you upgrade a production system that relies on any of them.

### REST API Errors

Every `/api/v2` endpoint now reports failure with the HTTP status code and an RFC 7807 `application/problem+json` body, and no longer returns `200 OK` with `{"success": false}`. Validation failures on settings return `422` or `400` with an `errors` object whose keys are dotted setting paths, creating a resource returns `201 Created` with a `Location` header, and deleting one returns `204 No Content` with no body. The users and roles endpoints return a fixed set of fields rather than the whole stored user or role. Integrations that read a `success` flag or a `message` field from the response body must read the status code and the problem body instead. SCIM keeps its own RFC 7644 error format, and the MCP tools are unchanged. The older data endpoints are no longer available under `/api/v2`, so integrations that call them must move to the tag, collection, rule and alert endpoints. See [REST APIs](../Integrating_to_Profinity/APIs/index.md).

### Data Locations

Linux moves from `~/.local/share/Prohelion/Profinity` to `/var/lib/prohelion/profinity`. Windows stays at `%LOCALAPPDATA%\Prohelion\Profinity` and macOS stays at `~/.local/share/Prohelion/Profinity`, and on those platforms Profinity also moves data from `~/Documents/Prohelion/Profinity`, `~/Prohelion/Profinity` and the opposite-casing folder under the application-data location. Update backups, automation and Docker volume mounts that refer to the old Linux path. See [Artefacts Directory](../Installation/Artifacts_Directory.md).

### YAML Documents

Profinity writes every YAML document it owns with camelCase keys, lowercase file and folder names, and `version: "2.3"`. Older PascalCase files still load. Profinity rewrites an older `security.yaml`, `profile.yaml`, `config.yaml`, `theme.yaml` or `plugins.yaml` in the new format when it loads it, and rewrites other documents when it saves them, so only tooling that reads these files directly needs to change. Re-save collections and rules in the visual editors after the upgrade if you edit their YAML by hand. The `{COMPONENT_NAME}` placeholder in dashboards still loads and is saved as a relative or absolute tag path the next time the dashboard is saved.

### Firmware Passcodes

Gen2 battery management systems and Rinstrum scales no longer keep the firmware configuration key or setup passcodes in the profile. Users enter them in the component's settings dialog, and Profinity holds them only for that sign-in session, so anything that relied on a stored passcode must be unlocked again after each sign-in.

### BACnet Device Instance

The BACnet component now reads the Device object of the device at its **Remote host** and compares the instance with **Device instance**, and it reads no point of a device that reports a different number. A BACnet component that left **Device instance** at its default of `0` stops reading points until the setting is changed to the real instance of the device. The allowed range is now `0` to `4194302`. See [BACnet](../Components/Industrial_Protocols/BACnet.md).

### Auto Connect Replaces Auto Start

The setting that connects a component when the profile loads is now called **Auto Connect** on every component that holds a connection. Loggers, historians, publishers, the Tag Relay sender and the OPC UA server previously called it **Auto Start**, and the old setting is no longer read, so a profile that turned **Auto Start** off must have **Auto Connect** turned off. The MQTT Subscriber and Tag Relay receiver gain **Auto Connect**, on by default, and a **Connect** / **Disconnect** switch. Script components keep **Auto Start Script**.

### Connections Start in Error Instead of Failing

A component that connects to a broker, device, server or database no longer refuses to start when the other end is unavailable. It starts, shows **Error**, and retries every 5 seconds, or at its own reconnect setting. A component that used to show **Off** after a failed start now shows **Error**, and anything that relied on a start failure to detect a missing device should watch the status instead. The MQTT and Tag Relay subscribers retry at a steady interval instead of backing off to 60 seconds. For plugin authors, `ManagedConnection` in `Profinity.Sdk` replaces the need for a plugin to keep its own reconnect scheduler. See [Connections and Reconnecting](../Components/Connections_and_Reconnecting.md).

## Known Issues

- Tag Relay shares live tags between Profinity instances and needs the Data Relay feature on both instances. It exports a sender's full tag tree with no field-level filtering, and a single path collision rejects the whole batch from that sender. See [Tag Relay](../Tags/Tag_Relay.md).
- Reciprocal tag linking, such as adding a rule from the collections editor context menu, is not available in 2.3, although the Tag Explorer context menu flows work.
- Publishing plugins to a NuGet feed is not available in 2.3, so install a local `.nupkg` or zip through the Plugin Manager.
- The central firmware updater is not part of 2.3. Each component flashes its own firmware.
- Android emulators cannot receive local network UDP heartbeat broadcasts, so test mobile discovery on a physical device. See [Profinity Mobile](../Mobile/index.md).
