# Profinity 2.3 engineering open questions

**Raised by:** the 2.3 documentation quality pass (October 2026). **Not published:** this page is under `docs/internal/` and is excluded from the built site.

Each item is something the docs now state, or avoid stating, because the code did not settle it. Tick an item when engineering has confirmed it, and tell the documentation owner so the page can be changed. File references are in the Profinity repository.

Settled during the pass and no longer open: the time-window default (`-10m` everywhere), the BACnet device instance check, the Windows Desktop login and loopback behaviour, Industrial Protocols as an add-on on stock licences, the Rinstrum chart window, and the release notes page name.

## Defects to check first

- [x] **CAN replay may not transmit on the bus.** Settled: replay never transmits. `TransmitOverNetwork` and its `SendMessage` branch were removed from `CanBusReplayService`, with a scenario guarding it (`can-replay-isolation.feature`). Send and Receive page says "never".
- [x] **`publishStateTagPath` is missing from `rules.schema.json`** (settled: added to the schema and the AI Skills copy, with a save-validation scenario), and the rule item rejects unknown properties. `RulesYamlSchemaValidator` runs on save (`ProfileRulesYamlPersistence.cs:54,191`), so saving a rule that sets it may fail. The docs describe the setting only through the **Publish state tag path** editor field.
- [x] **Themes and branding have no licence entitlement** (settled: `ProductFeature.Themes` added to Desktop, Server, Enterprise and Trial; an unlicensed host serves the default theme. Commercial still to sign off the Licensing and Theming wording) in `ProductFeature.cs`. The Licensing page says Desktop and above with white-label rights, and the Theming page says Profinity does not block an unlicensed instance. Add the entitlement, or change the commercial position (Commercial to sign off the wording).
- [x] **MQTT Publisher in JSON mode never reconnects.** (settled: JSON mode now uses the shared `ConnectionMaintainer` with the same 5 second delay as Sparkplug B; the initial connect is still not retried) The connection is made at start and `SendAsync` throws when it is lost (`MqttPushTransport.cs:105-110`, `PushPayloadPublisherBase.cs:166-168`). The 5 second reconnect applies to Sparkplug B only (`MqttPublisher.cs:163`). The page now says a lost connection stays in **Error** until the logger is restarted.
- [x] **Release notes claims taken from the plans** need confirming before publishing: the REST error shape (A30), the firmware passcode change (A12), documents rewritten on load or save (A24), and `config.yaml` rewritten on save. Verified in code: the REST error shape (RFC 7807, 422 with an `errors` object, 201 with Location, 204 on delete), firmware credentials held per sign-in session (`FirmwareSessionCredentialResolver`, keyed by the token id), and the Linux data path. Corrected: documents migrated on load include `config.yaml`, `theme.yaml` and `plugins.yaml` as well as `security.yaml` and `profile.yaml`. The release notes are updated.
- [x] **Windows service:** settled from the code. `ProfinityService.cmd` registers `Profinity.exe` (the Desktop GUI, which starts the engine with `isDesktopHost: true`), so the service is a desktop host: it binds to loopback only and a Server licence does not change that (`LicenseNetworkPolicy`, covered by `EnforceRemoteWebServerPolicy_DesktopHost_ForcesLoopbackEvenWithServerLicense`). The service page now says so. Still open: `Running_As_Service.md` also says Profinity runs in server mode on Windows; the only Windows host in source is the desktop application, so confirm whether a non-desktop Windows server host exists.

## Tags, rules and alerts

- [x] **Defect fixed: a nested component's own rules were scoped to its name, not its mount path.** `RulesYamlLoader` now resolves the base prefix from the active component's mount root (Tag tree path plus name), so a `Charger` at `Vehicles/Car1` scopes `DBC` to `Vehicles/Car1/Charger/DBC`. Rule ids still derive from the component name. Covered by `RulesYamlLoaderNestedComponentScopeTests`; the Tag Tree Path page now says so.
- [x] `relatedTags` is stored with a rule but the Alerts Log detail dialog (`AlertDetailDialog.tsx`) does not show it. Settled: the detail dialog now lists them under RELATED TAGS.
- [x] The Alerts Log offers Acknowledge and Silence (fixed 1 hour) but has no Unacknowledge control; the docs say Unacknowledge is API only. Settled: an acknowledged alert now shows an Unacknowledge alert button.
- [x] `Math.Abs` and `Math.Round` on a nullable double in derived tag formulas: settled by test. They do not compile when passed `a.Value` directly (the expression library has no nullable overloads and the engine deliberately does not change `Math`). `Math.Abs(a.Value ?? 0)` and `a.Value != null ? Math.Abs(a.Value ?? 0) : null` work, and the Tag Expressions page now shows those forms. The documented examples `Math.Abs(a.Value - b.Value)` and `Math.Round(a.Value * 100, 2)` had never compiled. Possible follow-up: a friendlier compile message that suggests `?? 0`.

## Components and protocols

- [x] **BACnet identity check proved against the standard without a device (2026-10-10, no physical device available).** `BacnetSimulatorTests` run the real client against (1) an in-process BACnet/IP device built on the BACnet library and (2) `RawBacnetResponder`, which builds and reads the packets by hand from ASHRAE 135 (BVLC 0x81 0x0A, Device type 8, property 75, service 12, ComplexACK), so a fault in the library's own encoder cannot hide. Sources: ASHRAE Addendum 135a-5 (the responding device treats Device 4194303 as its own Device object), and the Chipkin ReadProperty reference for the error classes and codes. They found and fixed a real defect: on a computer with more than one IPv4 interface the client threw "Cannot determine the BACnet/IP broadcast address"; it now passes the local address the OS would use to reach the device. Also learned: a device that rejects the wildcard answers with a BACnet Error (not silence), and the message now says so. Not covered: a vendor's quirks, BBMD and router cases, segmentation, and devices on a UDP port other than 47808 (the component takes an IP address only).
- [x] **OPC UA server default fixed (2026-10-10):** the default Bind URL is now `opc.tcp://127.0.0.1:4840/Profinity`, and `0.0.0.0` or `localhost` are treated as `127.0.0.1`, so the server listens on loopback only (it listened on every interface before). A host name or IP address of the computer is the deliberate way to accept other computers, and the server certificate is replaced when it does not name the new address. Covered by `OpcUaServerBindingTests`, which reads the operating system's listeners. Release note added. Answered from code 2026-10-10: **Use security** passes `useSecurity` to `CoreClientUtils.SelectEndpoint`, whose library documentation says it selects an endpoint that uses security. The `opcua_pki` folder is `LocalApplicationData/Prohelion/Profinity/opcua_pki`, so it ignores `PROFINITY_HOME` and the Linux data folder: in Docker it is in the container, not the volume, and certificates are lost when the container is recreated. Engineering decision needed: move it under the artifacts directory (needs the path passed to the plugin).
- [x] **Read failures log at debug level** settled: a shared `OutageLog` now reports a failing read, poll, write or send once per outage (a warning with the reason, repeats at debug, a note when it works again) in the Modbus, BACnet, S7, EtherNet/IP, OPC UA and Rinstrum plugins, the MQTT publisher, Tag Relay sender, SQL and InfluxDB historians and loggers, the Prometheus logger and the TDK and Siglent chargers. Point-level wiring is covered by the helper's unit tests; there is no per-component log-capture test.
- [x] EtherNet/IP: the CIP path guidance is on the EtherNet/IP page, from the libplctag wiki (Tag String Attributes): the path is required for ControlLogix and CompactLogix, must not be set for Micro800 (the plugin already clears it), and is ignored for PLC-5, SLC 500 and MicroLogix unless it is a DH+ bridge route. So the default `1,0` is harmless for PLC-5 and SLC and no code change is needed. A route through a bridge is entered as pairs of port and address.
- [x] TAG SQL Historian: example connection strings for all five providers and the permissions (insert, select, and create table when Auto Create Table is on) are on the page. Still unverified: the SQLite default location, because the code uses the path you enter.
- [x] InfluxDB v2 and v3 historians: InfluxDB Cloud is supported (both historian pages say so) and the stale code comment is fixed. Still open: the token permissions the historians need.
- [x] Prometheus logger: **Server Hostname** is the host the listener answers to (prometheus-net `MetricServer`). The page now says `localhost` is reachable only from the same computer, `+` or the host name accepts remote scrapes, and Windows needs a URL reservation (`netsh http add urlacl`, from the prometheus-net README). From the library documentation, not tried against a live Prometheus; whether `0.0.0.0` works was not documented and is not claimed.
- [x] Prohelion Cloud Dashboard: the access token and device ID are shown in the customer's account on the Prohelion Cloud dashboard (the page now says so). Still open: whether the firewall note should name the cloud host (hard-coded in `ProhelionCloudDashboardSettings.cs:49`, outbound port 1883).
- [x] Tag Relay JWT: decided that the sender uses the token of a service account on the receiving instance (sender and receiver pages say so). Still open: whether `POST /api/v2/Relay/delta` is public API, and what happens with zero HTTPS receiver components.
- [x] Webhook retry numbers (3 attempts, 1 s, 2 s, 10 s) confirmed by the owner on 2026-10-09 and the code comment updated. Still open from this item: the publisher start gate discards the failure reason (`LoggerDeviceBase.cs:74-79`).
- [x] Chargers: a TDK or Siglent supply is connected manually with the Connect / Disconnect toggle in its menu, and a D1000 Gen2 charges through the Charge screen once Control Pack is on (both on the Chargers and Battery Management Systems pages).
- [x] BMS firmware: the Admin key is not published, and the page says to contact Prohelion; Peak and CANdapter adapters appear as SocketCAN on Linux, so use the SocketCAN or SocketCANd adapter there (CAN Bus Adapters page). Still open: which tab of the settings dialog shows the Firmware Configuration Key row.
- [x] WaveSculptor200: confirmed. The WaveSculptor22 component monitors both controllers. The WaveSculptor200 DBC on the Prohelion docs site (`Motor_Controllers/WaveSculptor200/User_Manual/DBC.md`) has the same 16 messages and the same 51 signals, with identical definitions, as the component's `WaveSculptor22.dbc`. The Motor Controller page and Full Example note were corrected; an earlier claim of a different Status layout and extra signals was wrong.

## Connection behaviour (added with the shared connection work)

Settled: everything that connects now retries from the start through `ManagedConnection` (see `Docs/Architecture/System/connection-management.md` in the Profinity repository). Open points for engineering:

- [x] **Backoff was dropped.** Decided: the MQTT and Tag Relay subscribers keep a steady 5 s retry; no backoff option.
- [x] **Rinstrum firmware settings reload** now runs on every established session (the controller raises `SessionEstablished`), so a scale that connects late or reconnects reloads them. Settled.
- [x] **BACnet identity check** now runs as part of opening the connection: a wrong or silent device shows Error with the reason and is retried every Reconnect delay; a device replaced after a failed read is caught the same way. Real-device trial still open under Components and protocols.
- [x] **Poll-loop base (G5)** done: Modbus, BACnet, S7, EtherNet/IP and OPC UA client controllers derive from `PolledDeviceController<TPoint>` in the SDK (about 900 fewer lines). Rinstrum (telemetry session) and the OPC UA server (listener) do not poll points, so they stay as they are. The poll-fault test now checks the base, and a guard test stops a plugin writing its own loop.
- [ ] **Customer docs** now describe the new behaviour (a Connections and Reconnecting page, the component pages and the release notes), but the Rinstrum component has no customer page to update.
