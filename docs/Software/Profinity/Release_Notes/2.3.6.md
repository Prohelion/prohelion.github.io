# Profinity 2.3.6 release notes

Profinity 2.3.6 compares every tag path exactly, including capitals, and it logs and publishes text, dates, identifiers, and lists as well as numbers.
The M48 Gen2 shows its cell voltages and temperatures, and Profinity removes a component that fails to start.
These notes are for a system already on Profinity 2.3.
To move a Profinity 2.2 system to 2.3, follow the [Profinity 2.3.3 release notes](2.3.3.md) and refer to [Profinity 2.3 breaking changes](Breaking_Changes_2_3.md) for what changed from 2.2.

## Tag paths

[Tag paths](../Tags/Selecting_Tags/Tag_Paths.md) is the reference for how a path is written.
This release is the build that applies those rules on a system already running Profinity 2.3.
Earlier 2.3 builds matched a path without regard to capitals, and they left a relative path unchanged when it already began with its starting point.
The [tag paths](Breaking_Changes_2_3.md#tag-paths) section of the breaking changes lists the same rules for a move from Profinity 2.2.

A relative path is always read under its starting point, even when it begins with the same text.
A group scope of `Pack1/Cells` inside a scope of `Pack1` means `Pack1/Pack1/Cells`.
A script on a component named `GPS Unit` that reads `GPS Unit/position/latitude` looks under `GPS Unit/GPS Unit`.
Start the path with `/` to read it from the root of the tag tree.
`.` means the current folder, `..` means the folder above, and a doubled slash is the same path as a single slash.
A dashboard bind that starts with `/` is used as written, and a bind with no leading `/` is read from that dashboard's component.

`Pump` and `pump` are different tag names.
A scope, a dashboard bind, a script path, a derived tag's dependency, and a tag expression all follow that rule, so `tag.MatchesPath("pump")` does not select the tags under `Pump`.
Search in **TAG EXPLORER** ignores capitals, because a search is not an address.
When the profile loads, the [logs](../Administration/Logs_Config.md) name each path that matches nothing as written and would match if capitals were ignored, and they give the spelling to use.

On the **DESIGN** tab and the **YAML** tab, Profinity checks a path as you type it and again when you save, and the message names the field.
A rule, collection, or derived tag that already holds a path no tag can be called is skipped when the file loads, and the other items in the file load.
**Tag tree path** and **Receiver tag path prefix** are checked the same way.

Add and rename treat a name that differs from another component only in capitals as already taken, and they show the usual duplicate-name message.
Each component is a folder, and that folder name is compared without regard to capitals.

A rule created from selected tags opens in the profile rules under the name **New rule**, so you can give it a name.
A rule created from a component dashboard stays on that component.
A rule for the whole tree keeps the name **All tags**.

## Logging, history, and publishers

An InfluxDB historian or logger stores a list, such as a firmware table, as JSON text, for example `[0,500,1000]`.
In Profinity 2.3.5 an InfluxDB v2 historian in **Snapshot** mode logged `writing failed` and wrote nothing while any tag held a list.

Text, a date, and an identifier are written to a `text` field, and the kind of value is written to `valueType`.
The historians read that history back as the same kind of value.
[InfluxDB historians](../Components/Historians/InfluxDB_Historians.md) describes the fields, and [What each destination holds for a tag](../Components/Logging_Modes.md#what-each-destination-holds-for-a-tag) covers every destination.

A dashboard at a past time, and stepped history, return values from the InfluxDB v2 and v3 historians.
In Profinity 2.3.5 the InfluxDB v2 historian returned an empty result for a past time, and the InfluxDB v3 historian missed readings with some server versions.
[How to view a dashboard at a past time](../How_To_Guides/View_Dashboard_at_a_Past_Time.md) explains the control.

The TAG Local Historian, the TAG SQL Historian, and the InfluxDB historians read every kind of value back the same way.
A TAG SQL Historian with an empty connection string can be added, started, checked, and removed, and a history read returns no rows.

A new tag logger, historian, publisher, or [Tag Relay Sender](../Components/Tag_Relays/Tag_Relay_Sender.md) opens with **(All Tags)** selected under **Collections**.
**Save** requires a collection, and the component starts once a collection is selected.
A CAN logger records the bus, so it has no **Collections** setting.
[Configure data logging](../How_To_Guides/Configure_Data_Logging.md) has the shared steps.

The MQTT Publisher with **JSON**, and the Webhook Publisher, send numbers, text, dates, identifiers, lists, and true or false.
A list is sent as a JSON list.
In Profinity 2.3.5 these publishers omitted every tag that held anything other than a number, and they wrote no message.
The [MQTT Publisher](../Components/Publishers_and_Subscribers/MQTT_Publisher.md#payload-formats) and the [Webhook Publisher](../Components/Publishers_and_Subscribers/Webhook_Publisher.md#payload-format) show the payloads.

The MQTT Publisher with **Sparkplug B** publishes each tag with its own type.
In Profinity 2.3.5 every tag went out as a double.
A tag that is new, or whose kind of value has changed, is announced before its data.

InfluxDB and the publishers differ from Profinity 2.3.5 for four kinds of value.

- Text that looks like a number, such as `12.5`, stays text.
- A Good tag with no value is left out. In Profinity 2.3.5 it was written to InfluxDB, and sent by a publisher, as `0`.
- A whole number above 9,007,199,254,740,992 is stored in the `text` field, so the digits stay as written.
- A derived tag whose expression returns a list reports Good quality and holds the list as JSON text. In Profinity 2.3.5 that tag reported Bad quality.

When a destination skips a tag, the [Logs](../Administration/Logs_Config.md) page under **ADMIN** shows one warning.
The warning names the tag, the destination, and the reason, and it is written once.
The reasons are a number that is not finite, text longer than the 64 KB limit of an InfluxDB text field, a text tag on the [Prometheus Logger](../Components/Loggers/Prometheus_Logger.md) when **Log** is **Values only**, and a tag whose value Profinity cannot read.
Profinity writes the tags that follow a value it cannot read.

The [Prometheus Logger](../Components/Loggers/Prometheus_Logger.md) has a new **Log** setting.
**Values only**, the default, serves numbers and true or false, and now leaves a text tag off the page, where Profinity 2.3.5 listed it as `NaN`.
**Values and text** also serves each text tag as an info line that carries the text.
Each Prometheus Logger now serves only its own tags, so a tag that a logger no longer exports leaves its page when the logger restarts.
The number on each line is now the tag's current value. In Profinity 2.3.5 the labelled line stayed at `0`, and the value appeared on a second line with no labels.

Starting a replay of a tag log or a CAN log that is missing from disk reports that the log was not found.

## Components

The [M48 Gen2](../Components/Battery_Management_Systems/Prohelion_BMU/index.md) reads cell voltages and temperatures from the CAN database shipped with the component.
Add it while the pack is sending, and the dashboard shows the cell voltages and temperatures.
A signal the database does not describe has no value.
The database describes two nodes, 14 cells, and four temperature sensors.
Earlier builds of Profinity 2.3 asked for the previous signal names, so the cells stayed blank and adding the component failed once the pack was sending.

When a new component fails after it has started, Profinity removes it and reports "The component could not be started, so it was not added. Check the logs for more details".
The profile and the tag tree stay as they were.
A component that is already in the saved profile keeps its settings and its files.
The add form offers the next free name, such as `Name 2`, when the name you asked for is taken.
A rename that fails leaves the previous name in place, and Profinity reports the failure.

**ADD COMPONENT** and removing a component need the **Modify components** permission.
Switching the active profile, uploading images, and flashing firmware need **Modify profiles**.

On a Generation 2 battery management system, **Save** accepts a valid **OCV values associated with its index as state of charge** table, under **State of charge**.
The table scrolls inside its own rows on the firmware settings panel.

## Tag Explorer and collections

The **Value** column in **TAG EXPLORER** sorts again as new samples arrive.
When the tags for a collection fail to load, the message gives the reason, in the tree and beside the collection filter, and the filter stays available so you can choose another collection.

Deleting a collection that a rule uses opens **Cannot delete collection** and names the rules.
A rule inside a group counts, and so does a group whose scope names the collection.
Remove those references, then delete the collection.

A preview of a tag expression shows the first 50 tags the signed-in user can see, and it says when further tags match.

## Accounts and the API

A [service account](../Administration/Users_and_Access/Service_Accounts.md) keeps its token when an administrator changes the account's roles, and the permissions follow the roles as they stand.
Switch the account off and that token ends.
Switch it on again and select **Generate Token** to issue a token that works.
**Generate Token** on an account that already has a token replaces the old one at once.

The Swagger page lists tags, rules, collections, derived tags, expressions, history, alerts, profiles, the active profile, the CAN bus, DBC, actions, and sign-in.
The administration calls that the web interface uses keep working.
Refer to [APIs](../Integrating_to_Profinity/APIs/index.md) for the calls the documentation covers.

Profinity AI in the desktop window signs its connection with the desktop window's own sign-in, and that sign-in is accepted on the computer running Profinity.

## Copy, dashboards, and the side menu

**Copy** works when you open Profinity over plain HTTP, including a container on the local network.
A copy that fails raises an error notification.
The error page says the report went to the Prohelion team when the send succeeded.

After you add or delete a profile, the list updates on the profile page.
The desktop window stays on that page.

The tag tree menu and its sub-menus open inside the screen.
Hotspot icons and their alert badges on an interactive image stay inside the image card, including on a compact dashboard.
On a phone, a tap opens a group in the side menu.
On the desktop, the component list and the lower part of the side menu each scroll on their own, and the header stays in place.

The title of a multi-line setting lines up with the top of the box.
A long text setting fills the height left on its tab.

## Upgrading from 2.3.5

After the first start, open the [logs](../Administration/Logs_Config.md) and correct each path the warning names, using the spelling in **TAG EXPLORER**.
A relative path that repeated its starting point, such as `Pack1/Cells` under a scope of `Pack1`, is read as `Pack1/Pack1/Cells`.
Start that path with `/` when it should begin at the root of the tag tree.

An Influx query or a subscriber that read `12.5` as a number, or that read a Good tag with no value as `0`, receives text or no sample.
Accept text, and treat a missing sample as no value.

A service account you have switched off needs a new token from **Generate Token**.
Changing its roles keeps the token it already has.
